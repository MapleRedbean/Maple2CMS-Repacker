This project contains the definitive, working implementation of the Orion2 pack file encryption scheme used by MapleStory2 (.m2h/.m2d files).

### Critical Crypto Parameters (from CipherKeys.cs)

- **OS2F_USER_KEY**: 256 rows × 32 bytes (AES-256 key table for OS2F/PS2F)
- **OS2F_IV_CHAIN**: 128 rows × 16 bytes (IV table for OS2F/PS2F)
- **MS2F_USER_KEY**: 256 rows × 32 bytes (AES-256 key table for MS2F/NS2F)

### Key Derivation

**OS2F/PS2F**:
- keyOffset = compressedSize & 0x7F
- ivOffset = (compressedSize >> 7) & 0x7F

**MS2F/NS2F**:
- keyOffset = compressedSize & 0xFF
- ivOffset = (compressedSize >> 8) & 0x7F
- MS2F IV = 0x35 0x35 ... XOR IVChain[ivOffset]

### Decryption Pipeline
1. Base64 decode encrypted data
2. AES-CTR decrypt (key from USER_KEY[keyOffset], iv from IV chain)
3. zlib decompress if buffer_flag & 0x10

## 11:07 Update — struct.unpack_from Bug Explained

### Root Cause
`struct.unpack_from` with a single format code returns a **tuple of one element**, e.g., `(42,)`.
```python
# WRONG — tries to assign 1-element tuple to 2 variables
self.reserved, off = struct.unpack_from('<I', data, off); off += 4
# TypeError: not enough values to unpack

# CORRECT — extract the single value with [0]
self.reserved = struct.unpack_from('<I', data, off)[0]; off += 4
```

### Fix Applied
The user needs to replace all header unpacking lines in `orion2_v2.py` `StreamHeader.__init__` with `[0]` indexing.
See full explanation in the conversation turn.

### User Plan
User will manually fix the struct bug, then re-run `orion2_v2.py` to test decryption against Gfx.m2h / Image.m2h / etc.

## 12:42 Update — Critical AES-CTR Fix Required

### The Bug: Wrong AES-CTR Implementation

`orion2_v3.py` uses PyCryptodome's built-in `AES.MODE_CTR`:
```python
cipher = AES.new(key, AES.MODE_CTR, nonce=iv[:8])
decrypted = cipher.decrypt(raw)
```

**This is wrong.** It does NOT match the C# `AESCipher` implementation.

### C# AES-CTR Behavior (MUST replicate manually)

The C# `AESCipher.cs` uses **ECB mode** to encrypt the full 16-byte counter (the IV itself):

```csharp
pCounterEncryptor = pAlgorithm.CreateEncryptor(aUserKey, new byte[BlockSize]);

// For each block:
pCounterEncryptor.TransformBlock(aCounter, 0, aCounter.Length, pXORBlock, 0);  // Encrypt counter (ECB)
IncrementCounter();  // In-place big-endian increment of aCounter
pDest[...] = pSrc[...] ^ pXORBlock[...];  // XOR
```

Key differences from PyCryptodome CTR:
- **Full 16-byte counter** — no "nonce" vs "counter" split
- **In-place big-endian increment** — the entire IV is incremented
- **ECB mode** — encrypt the counter, not a nonce+counter combo
- Counter increments like a big-endian integer: `00 00 ... 01 00` → `00 00 ... 01 01`

### Correct Python Implementation

```python
def aes_ctr_decrypt_manual(key, iv, ciphertext):
    """Manually implement C# AES-CTR matching AESCipher.cs"""
    cipher = AES.new(key, AES.MODE_ECB)
    counter = bytearray(iv)
    plaintext = bytearray()
    
    for i in range(0, len(ciphertext), 16):
        # 1. Encrypt counter with ECB
        xor_block = cipher.encrypt(bytes(counter))
        
        # 2. XOR decrypt
        block = ciphertext[i:i+16]
        for j in range(len(block)):
            plaintext.append(block[j] ^ xor_block[j])
        
        # 3. Increment counter (big-endian, in-place)
        for k in range(15, -1, -1):
            counter[k] = (counter[k] + 1) & 0xFF
            if counter[k] != 0:
                break
    
    return bytes(plaintext)
```

### Also: Base64 Decode is on UTF-8 STRING, not raw bytes

The C# code does:
```csharp
pSrc = Convert.FromBase64String(Encoding.UTF8.GetString(pSrc));
```

So the raw bytes from the file are first decoded as UTF-8 to a string, THEN base64-decoded. This is non-standard (usually base64 works on raw bytes). Test this order.

## 13:34 Update — Header Struct Parsing Bug Found & Fix In Progress

### Critical Bug: Incorrect struct.unpack Offsets

The earlier scripts were manually slicing header bytes at wrong offsets, causing `compressed_header_size` to be read as enormous values (e.g. 39 trillion) instead of the correct small values. This led to **wrong key indices** and complete decryption failure.

### Correct Header Parsing (verified with struct.unpack)

**MS2F header** (68 bytes after 4-byte magic):
```python
(reserved, cds, eds, hs, chs, ehs, fc, dsz) = struct.unpack('<IQQQQQQQ', hdr)
# I=4bytes, Q=8bytes → 4+8*7 = 68 bytes ✓
```

**OS2F/PS2F header** (56 bytes after 4-byte magic):
```python
(fc, reserved, cds, eds, chs, ehs, dsz, hs) = struct.unpack('<IIQQQQQQ', hdr)
# I=4bytes*2, Q=8bytes*6 = 56 bytes ✓
```
